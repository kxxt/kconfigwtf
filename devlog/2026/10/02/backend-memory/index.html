Recommended implementation

Every occurrence owns:
kernel: "6.12.0-…/amd64"
value: enum + optional String
→
Each occurrence: 8 bytes
kernel_id: u32, value_id: u32
Strings stored in shared tables
  1. Use a server-specific compact representation. Keep each package's entries in a sorted array searched by config name. Each entry holds one exact-sized array of integer pairs; kernel metadata and repeated value strings live in per-package tables.
  2. Load one file at a time. Deserialize compact JSON directly, avoiding the generic untagged deserializer and its expanded string representation. Preserve legacy-index support through a per-file conversion using the existing loader. Keep validation of references and existing error behavior.
  3. Build records only for the requested config. Preserve API response content, ordering, missing-value behavior, raw URLs, architecture spellings, cache headers, and ETags. Keep the on-disk schema, indexers, CLI, and frontend unchanged. No new dependencies, disk cache, or allocator change.
  4. Verify the result. Add focused compatibility tests; run existing tests, formatting and Clippy; compare full-dataset API responses against the baseline; measure startup, idle, and 80 requests at concurrency 8. Target less than 500 MiB for measured peak as well as idle. Record results and the storage design in developer documentation.

This design retains the complete lookup data in RAM and needs no writable service directory. Future dataset growth or substantially more concurrent traffic can still raise memory use. If measurements miss the target, further design changes come back here for your decision.
